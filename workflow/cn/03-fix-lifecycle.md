# 工作流 3：fix_<desc>.md 生命周期（缺陷反馈闭环）

> 场景：用户给出 review、测试失败、人工验收 bug，或要求做审查 / 计划复核。
> 适用范围：**仅限对已完成内容的修复**。若用户提出的是 plan 之外的新功能或新模块，请走 [05-plan-revision.md](05-plan-revision.md)（fix-plan 生命周期）。

## 与 fix-plan 的边界

| 触发情境 | 走 `fix_<desc>.md` | 走 `fix-plan_<desc>.md` |
| --- | --- | --- |
| 实现存在 bug、回归 | ✅ | ❌ |
| 审查 / 安全审计指出的现存问题 | ✅ | ❌ |
| 测试反馈出来的实际偏差 | ✅ | ❌ |
| 用户提出 plan 之外的新功能 / 新模块 | ❌ | ✅ |
| 用户要求扩展验收标准 / 调整功能范围 | ❌ | ✅ |

即使用户在同一次对话中同时给出两类输入，也必须**分别建两份文件**。

## 创建

新建语义命名文件，例如：

- `fix_mobile-layout.md`
- `fix_api-contract.md`
- `fix_security-review.md`

不要使用 `fix_01.md` 作为新文件名。

文件开头写清：

- 内容
- 时间
- 来源
- 范围

## 映射到 TODO

每条反馈都要落到 `TODO.md`：

- 能由代理修：进入具体 TODO 子项。
- 已无效：TODO 标 `[~]` 并写明废除原因。
- 被新方案覆盖：TODO 标 `[!]` 并指向新条目。
- 需要人工执行或人类决策：转 `HUMAN.md`；若阻塞具体执行，先建 TODO，再把阻塞指向 `HUMAN.md`。

## 推进

`fix_*` 优先级最高，高于 `fix-plan_*` 与普通 TODO。任一未归档 fix 有未完成代理事项时，先处理 fix，再继续后续工作。

## 归档

当本批次所有条目都已完成、废除或转人工，且无代理可执行事项残留：

1. 汇总"对 `plan.md` 的影响"。
2. 仅在现状与 plan 描述出现偏差时回写 `plan.md`；常见的纯修复情形通常无需回写。
3. 移入 `.cairn/archive/fix_desc-YYYYMMDD.md`，desc 保持原文件名语义。
4. 对应 TODO 子项标记完成或保持人工阻塞。

## 与 plan 修订的关系

`fix_<desc>.md` 不是新增 plan 内容的入口，仅在归档时按需修正描述偏差。新增 / 扩展 plan 的范围必须走 `fix-plan_<desc>.md`，详见 [05-plan-revision.md](05-plan-revision.md)。

## 反模式

- 把"用户提出的新功能"塞进 `fix_<desc>.md`（应走 fix-plan）。
- 把缺陷反馈和新功能合并到一个文件，因为是同一次对话提的。
- 代理把自己临时发现的小问题擅自塞进 fix。
- 把多批不同来源反馈合并到一个文件。
- 只在 fix 里打勾，不同步 TODO。
- 人工验证或方向决策留在 fix 里长期阻塞。
